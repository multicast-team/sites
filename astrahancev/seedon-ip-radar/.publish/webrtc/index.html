WebRTC Как возникает утечка?

WebRTC (Web Real-Time Communication)Технология, встроенная в браузер, Позволяет совершать видеозвонки без дополнительных плагинов, а также общаться голосом и передавать файлы. Это удобно?

Но нужно учитывать: WebRTC При установлении соединения, использует STUN сервер получает внешний сетевой адрес IP. При этом используется UDP Протокол, а многие прокси поддерживают только TCP Трафик. В результате — Даже когда обычный веб-трафик проходит через прокси, WebRTC другой протокол может раскрыть фактический IP адрес.

Кроме того, На веб-странице JavaScript проверка может выполняться без отдельного уведомления WebRTC, и не требует отдельного окна разрешения.

Что проверяет инструмент?

Инструмент обращается к нескольким STUN Сервер (Google, Cloudflare и др.)Отправляет UDP Запрос, Собирает возвращённые IP Адрес, чтобы показать:

  • Обрабатывает ли прокси UDP Трафик — Если STUN Если возвращён адрес прокси IP, это означает UDP используется ожидаемый прокси-маршрут
  • Наличие IP Утечка — Если STUN Возвращён адрес вашего оператора IP, это означает UDP Трафик обошёл прокси
  • Работают ли правила маршрутизации — Разные STUN серверы могут использовать разные выходные адреса, Сравните это с ожидаемыми правилами маршрутизации
  • IPv6 Есть ли утечка — Некоторые прокси обслуживают только IPv4, IPv6 Трафик может раскрыть. Результат показывает все найденные IPv6 Адрес

Простыми словами: Нажмите кнопку, чтобы узнать UDP какой маршрут использует трафик.

STUN и UDP Что это?

UDP (User Datagram Protocol)Один из базовых транспортных протоколов интернета. и TCP Разные, UDP Позволяет отправлять пакеты без предварительного соединения, Снижает накладные расходы, но не гарантирует доставку. Видеозвонки, Онлайн-игры, и голосовые звонки чувствительны к задержке, и часто используют UDP.

STUN (Session Traversal Utilities for NAT)Протокол помогает"определить внешний IP"адрес. Устройство часто находится за маршрутизатором (NAT), и не знает своего публичного IP какой адрес используется. STUN Сервер работает так: Вы отправляете UDP пакет, и получаете ответ"с адресом, который видит сервер IP Да X.X.X.X".

WebRTC использует STUN для прямого соединения устройств. Проблема в том, что: этот UDP пакет не обязательно идёт через прокси. Многие прокси обслуживают только TCP Трафик, UDP и пакет уходит через локальную сеть, Тогда фактический IP адрес виден STUN серверу.

Как определить утечку?

Сравните: выходной адрес прокси IP и WebRTC с обнаруженным IP.

  • Если адресасовпадают (или WebRTC или протокол отключён и адрес не получен IP) → Безопасность, утечка не обнаружена
  • Если WebRTC Если получендругой IP, и этот IP адрес принадлежит вашему оператору IP → обнаружена утечка

Страница автоматически сравнивает адреса, Ручное сравнение не требуется.

Если обнаружена утечка, Как исправить?

Firefox: Введите в адресной строке about:config, Найдите media.peerconnection.enabled, Двойным нажатием установите false. Это полностью отключит WebRTC.

Chrome / Edge: В браузере нет обычного переключателя отключения WebRTC соответствующая настройка. Можно использовать uBlock Origin Расширение, в"Настройки → Конфиденциальность"Отметьте"Блокировать WebRTC Раскрытие локального IP Адрес".

Brave: Откройте настройки → Конфиденциальность и безопасность → WebRTC IP Политика обработки, Выбрать"Отключить вне прокси UDP".

Safari: По умолчанию для WebRTC действуют ограничения, что снижает риск утечки. Дополнительные настройки доступны в"Разработка"меню ограничений WebRTC Функции.

Расширенная настройка: UDP Маршрутизация

Описанные выше способы"действуют на весь протокол" — полностью отключают WebRTC, или ограничивают его. Если протокол нужен для WebRTC (например Google Meet, Discord Голосовая связь), полное отключение может нарушить работу.

Другой вариант: В клиенте прокси для UDP задайте отдельный маршрут трафика. Проверьте поддержку правил для UDP соответствующего протокола, Можно направить STUN трафик серверов (например Google и Cloudflare для STUN Адрес)через выбранный выход, сохранив работу другого UDP Трафик (например игр, локальной сети). Это позволяет WebRTC защитить фактический IP, и не отключать протокол для всех приложений.

После изменения, повторите тест на этой странице, и проверьте результат.

Несколько выходных адресов IP?не обязательно означают WebRTC Утечка

Порядок проверки. Если обнаружено несколько разных публичных IP, этоне обязательноДа WebRTC Утечка.

Некоторые пользователи настраивают раздельные маршруты (например прямое подключение к российским ресурсам, и прокси для международных), другой STUN Разные серверы могут попадать под разные правила. Например:

  • Google для STUN Сервер → через прокси → показан выходной адрес прокси IP (например в Японии)
  • Cloudflare для STUN Сервер → используется другой маршрут прокси → показан другой выход IP (например в Гонконге)

В таком случае несколько разных IP Даэто нормально, поскольку правила направляют трафик через разные узлы. Сравните: результат с вашими правилами, Проверьте эти IP регионы: соответствуют ли они ожиданиям.

Особое внимание требуется:

если прокси включён, Но WebRTC а найденные публичные IP полностью относятся квашему локальному оператору IP (например при проверке из России, все адреса принадлежат российскому оператору IP), Это может означать WebRTC полный обход прокси, и пакет уходит через локальную сеть. если для этого трафика ожидался другой маршрут.

Простой способ проверки: Посмотрите геолокацию результата. Если она совпадает с вашим местоположением, а трафик должен идти через прокси, проверьте настройки — Используйте описанные выше"Если обнаружена утечка, Как исправить?"способы.

Помимо WebRTC, DNS утечка тоже важна

Проверка только одного протокола WebRTC Утечка, не исключает утечки через другой: Утечки DNS.

При каждом обращении к сайту, браузер сначала запрашивает DNS преобразование домена в IP Адрес. Если этот DNS запрос идёт вне прокси, и отправляется DNS вашего оператора DNS Сервер, оператор может видеть запрошенные домены.

Также: DNS в отличие от утечки WebRTC не всегда определяется простым сравнением адресов. Для проверки нужен отдельный инструмент DNS показывающий путь DNS-запроса.

Разница между двумя утечками:

  • WebRTC Утечка → и раскрыть фактический IP Адрес (сайт видит ваш сетевой адрес)
  • Утечки DNS → раскрываются запрошенные домены (оператор видит, какие домены запрашивались)

Проверьте оба протокола. WebRTC Текущий тест выполнен здесь, DNS Проверка другой утечки доступна на странице DNS Проверка утечек Страница, 5 с до результата, Проверьте ваш DNS на нежелательное раскрытие данных.

Почему режим системного прокси и TUN режим дают разные результаты

Иногда наблюдается такое различие: системный прокси показывает"Утечка не обнаружена", Переключить на TUN а другой режим показывает утечку. Причина может быть в доступности протокола, Два режима по-разному обрабатывают трафик.

Режим системного прокси (HTTP/SOCKS5): Браузер отправляет запросы через системный прокси, Но выбранный прокси может поддерживать только TCP Трафик. WebRTC для STUN использует протокол UDP, который не проходит через HTTP/SOCKS Прокси. В результате STUN Запрос не может быть отправлен, и страница показывает"Утечка не обнаружена".

TUN Режим (Глобальный/Виртуальный адаптер): TUN Создаёт виртуальный адаптер для перехвата трафика, Включая TCP и UDP. Это означает STUN для UDP запрос может быть отправлен. Если узел не поддерживает UDP Перенаправление, или UDP может использоваться другой выход, либо правила не охватывают STUN Адрес сервера, это приводит к UDP Выходной IP и TCP Выходной IP Не совпадает, и может определяться как возможная утечка.
